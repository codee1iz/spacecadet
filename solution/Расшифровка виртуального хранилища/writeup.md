## Суть

После того как мы разобрали логику проверки пароля и научились патчить прошивку, оставался главный вопрос: как получить доступ к самим данным. Виртуальное хранилище, которое устройство отдаёт по USB, хранится во флеш-памяти в зашифрованном виде. Нам нужно было понять алгоритм и восстановить исходные данные из дампа - без устройства и без пароля.

## Как искали функции шифрования

Мы отталкивались от цепочки вызовов. В главной функции устройства есть бесконечный цикл, который обрабатывает USB-события. Внутри этого цикла вызывается обработчик SCSI-команд - именно он отвечает за чтение и запись секторов хранилища. От него мы перешли к двум функциям, которые и выполняют шифрование: одна работает при чтении, другая при записи.

Внутри этих функций сразу было видно характерное: цикл по шестнадцатибайтовым блокам, XOR-операции с константами и генератор, зависящий от номера сектора. Всё указывало на потоковый шифр на основе XOR.

## Как поняли, что это XOR

Ключевой признак - операция исключающего ИЛИ. В коде каждый байт данных XOR-ится с байтом ключа, который генерируется на лету. Поскольку XOR - обратимый процесс, одна и та же операция работает и для шифрования, и для дешифрования. Это подтверждалось и структурой кода: обе функции - чтения и записи - реализуют один и тот же алгоритм, отличаются только точкой вызова.

## Как восстановили ключ

Ключ генерируется линейным конгруэнтным генератором, начальное значение которого зависит от номера сектора. Это значит, что для каждого сектора ключ свой, но вычисляется он детерминированно - зная номер сектора, можно воспроизвести ключ. Мы разобрали формулу генератора, извлекли шестнадцать констант, по одной на каждый байт в блоке, и собрали их в таблицу.

Важный момент: ключ зависит **только от номера сектора**. Пароль в генерации ключа не участвует. Это означает, что шифрование хранилища не связано с парольной защитой - пароль лишь управляет тем, отдаёт ли устройство данные по USB.

## Алгоритм генерации ключа

Ключ генерируется для каждого сектора отдельно. Начальное значение счётчика зависит от номера сектора и вычисляется по формуле:

```
seed = (952749472 * lba - 1640519190) mod 2^32
```

Каждый сектор разбивается на 32 блока по 16 байт. Для каждого блока генерируется свой набор из 16 байт ключа. Байт с номером `i` в блоке вычисляется как:

```
key[i] = ((v10 + C[i]) mod 2^32) >> 24
```

где `v10` - текущее значение счётчика, а `C[i]` - константа для этого байта. После генерации блока счётчик увеличивается на `1103515245`:

```
v10 = (v10 + 1103515245) mod 2^32
```

### Пример для нулевого сектора

Для `lba = 0` начальное значение счётчика равно `-1640519190` (в hex - `0x9E37A9EA`). Первый блок ключа получается таким:

```
00 9E 3C DA 78 17 B5 53 F1 8F 2E CC 6A 08 A7 45
```

Этот ключ подтверждён на реальных данных - XOR с ним даёт корректный загрузочный сектор FAT12.

## Как написали скрипт

На основе анализа псевдокода мы написали скрипт на Python. Он читает дамп флеш-памяти, берёт регион хранилища, для каждого сектора генерирует ключ и выполняет XOR. На выходе получается расшифрованный образ файловой системы.

Скрипт состоит из нескольких частей: функция генерации ключа для блока, функция обработки сектора и функция прохода по всему образу. Всё вместе занимает немного строк и работает быстро.

## Как проверили результат

После расшифровки мы открыли полученный образ в hex-редакторе. Первые байты начинались с сигнатуры FAT12 - это стандартный загрузочный сектор файловой системы. Значит, алгоритм восстановлен верно, и данные расшифрованы корректно.

## Что это дало

Мы получили полный доступ к содержимому виртуального хранилища - без устройства, без пароля, только из дампа флеш-памяти. Это подтвердило главный вывод: парольная защита и шифрование хранилища существуют независимо друг от друга, и обход пароля не требуется для доступа к данным, если есть дамп.

## Итог

В репозиторий приложены оба файла: исходный дамп флеш-памяти и уже расшифрованный образ хранилища. Первый можно использовать для самостоятельного анализа, второй - для проверки результатов или работы с содержимым без повторной расшифровки.

Для запуска скрипта расшифровки используется следующая команда:

```
python decrypt.py firmware.bin firmware_decrypt.zip
```

Первый аргумент - путь к дампу прошивки, второй - имя файла, куда будет сохранён расшифрованный образ. Скрипт автоматически определит регион хранилища и обработает все секторы.
