## Суть

Получив дамп оригинальной прошивки, мы решили проверить, насколько далеко можно продвинуться без физического устройства. Основная идея заключалась в том, чтобы не переписывать логику проверки PIN и расшифровки хранилища самостоятельно, а запустить оригинальный машинный код прошивки в эмуляторе.

Для этого была создана программная модель необходимого окружения RP2040 на базе Unicorn Engine. В неё загрузили дамп Flash, выделили области RAM, добавили обработку обращений к периферии и реализовали минимальную эмуляцию SPI Flash. После этого стало возможно запускать отдельные функции оригинальной прошивки непосредственно в эмуляторе.

В результате через эмулятор удалось выполнить два ключевых действия: перебрать PIN с использованием оригинальной функции его проверки и запустить оригинальную функцию расшифровки содержимого хранилища.

## Подготовка

Работа велась с бинарным дампом Flash, полученным ранее через BOOTSEL. Для запуска прошивки в Unicorn необходимо было восстановить не только сам ARM-код, но и окружение, с которым он взаимодействует во время работы.

В скрипте были выделены области Flash и RAM, после чего в них загружалось содержимое дампа. Для прошивки использовался режим ARM Thumb, соответствующий коду микроконтроллера. Дополнительно были отображены области адресного пространства, используемые периферийными блоками RP2040.

Часть обращений к аппаратным регистрам нельзя было просто оставить без обработки. Поэтому для них были добавлены hooks Unicorn: при чтении определённых адресов эмулятор возвращает значения, которые прошивка ожидает получить от таймеров, PLL, генераторов тактовой частоты, SIO и других блоков. Аналогичным образом была реализована минимальная модель SPI Flash, позволяющая прошивке получать данные из исходного образа.

Таким образом, задача заключалась не в полной эмуляции RP2040, а в восстановлении именно той части аппаратного окружения, которая необходима для выполнения интересующих нас функций.

## Запуск оригинальной прошивки

После подготовки памяти и периферии скрипт выполняет начальную инициализацию прошивки. Дополнительно эмулируются некоторые действия bootrom, необходимые для нормальной работы кода: перенос `.data` в RAM и разрешение используемых ROM-функций.

Некоторые инструкции и циклы, связанные непосредственно с аппаратным окружением, пришлось нейтрализовать. Например, в прошивке присутствуют циклы ожидания готовности аппаратных блоков и инструкции работы с `PRIMASK`, которые Unicorn не может корректно обработать в используемом режиме. Такие участки заменяются на NOP либо получают заранее заданные значения через hooks.

После этого прошивка может выполняться в эмуляторе до перехода в рабочее состояние.

## Проверка PIN

Следующим этапом мы перешли непосредственно к функции проверки PIN. При анализе прошивки была найдена соответствующая функция по адресу `0x0C78`. В скрипте этот адрес используется как точка входа, поэтому для проверки не пришлось воспроизводить алгоритм сравнения на Python.

Идея заключается в следующем. Для очередного кандидата формируются четыре цифры:

```
0000
0001
0002
...
9999
```

Полученные четыре байта записываются в ту область памяти, из которой оригинальная функция ожидает получить введённый PIN. После этого управление передаётся непосредственно на адрес `0x0C78`.

То есть каждая попытка проходит через настоящий машинный код прошивки:

```
кандидат PIN
      ↓
запись в RAM эмулятора
      ↓
0x10000C78
      ↓
оригинальная проверка прошивки
      ↓
успех / ошибка
```

Для определения результата используются адреса переходов внутри функции проверки. При попадании на ветку успешного завершения эмуляция останавливается, после чего дополнительно проверяется флаг авторизации в памяти. Если его значение равно `1`, текущая комбинация считается найденным PIN.

Важный момент заключается в том, что здесь не реализовывалась отдельная копия алгоритма проверки. Эмулятор запускает именно функцию из исходного дампа, поэтому результат зависит от поведения оригинальной прошивки.

## Почему это сработало

Для проверки PIN прошивке не требовалось наличие самого физического токена. Функция использовала данные из памяти и выполняла обычные операции сравнения, поэтому необходимые входные значения можно было подать непосредственно через память эмулятора.

Аппаратные компоненты, которые действительно требовались прошивке, были заменены минимальными моделями и hooks. В результате функция проверки смогла выполниться в программной среде так, как если бы она получила данные от настоящего устройства.

Таким образом, физический ввод через энкодер оказался необязательным именно для этого этапа анализа.

## Запуск функции расшифровки

После получения возможности выполнять оригинальный код прошивки мы применили тот же подход к хранилищу. В прошивке была найдена функция расшифровки по адресу `0x354`.

Вместо самостоятельной реализации алгоритма расшифровки скрипт подготавливает регистры и стек в соответствии с ожидаемым интерфейсом функции, после чего передаёт управление непосредственно на `0x10000354`.

В `R1` передаётся номер сектора, в `R3` — адрес буфера назначения, а на стеке размещается размер обрабатываемых данных. После выполнения функции полученные данные считываются из RAM эмулятора.

Получается следующая схема:

```
зашифрованный сектор Flash
          ↓
   оригинальная функция
       0x10000354
          ↓
      RAM эмулятора
          ↓
   512 байт расшифрованных данных
```

Таким способом функция вызывается отдельно для каждого сектора зашифрованной области.

## Восстановление хранилища

После расшифровки отдельных секторов из них собирается единый образ диска размером 1 МБ. Скрипт обрабатывает 1408 секторов зашифрованной области и записывает результат в файл.

Дополнительно перед созданием полного образа выполняется проверка первого сектора. Полученные данные должны соответствовать структуре FAT12: в начале ожидается сигнатура загрузочного сектора `MSDOS5.0`, а в соответствующем поле — строка `FAT12`.

Таким образом, результат расшифровки проверяется не только по факту выполнения функции, но и по структуре полученной файловой системы.

## Как проверяли

После запуска скрипта сначала проверяется сам дамп прошивки. Скрипт ищет сигнатуру функции проверки PIN, проверяет адреса используемых данных и наличие констант, связанных с алгоритмом расшифровки.

После этого создаётся экземпляр эмулятора, выполняется инициализация прошивки и запускается перебор PIN через оригинальную функцию.

После нахождения PIN запускается функция расшифровки. Первый расшифрованный сектор проверяется на соответствие FAT12, после чего создаётся полный образ `token_disk.img`.

Полученный образ можно подключить как виртуальный диск и работать с восстановленным содержимым хранилища уже без выполнения кода на самом устройстве.

## Как это работает вместе

Весь вектор можно представить как последовательную цепочку:

```
Дамп прошивки
      ↓
Восстановление окружения RP2040
      ↓
Запуск оригинального кода в Unicorn
      ↓
Оригинальная проверка PIN
      ↓
Получение PIN
      ↓
Оригинальная функция расшифровки
      ↓
Расшифровка секторов
      ↓
FAT12-образ хранилища
```

При этом Python-скрипт выступает не заменой прошивки, а управляющей частью эмулятора. Он подготавливает память, передаёт параметры оригинальным функциям и получает результаты их выполнения.

## Почему это важно

Этот вектор показывает, что наличие физического устройства не всегда является обязательным условием для анализа защищённой функциональности. Если критичная логика реализована непосредственно в прошивке и не зависит от уникального состояния внешних аппаратных компонентов, её отдельные участки можно выполнять в восстановленной программной среде.

В данном случае удалось использовать оригинальный машинный код сразу для двух задач. Сначала он использовался для проверки большого количества вариантов PIN, а затем тот же подход позволил вызвать функцию расшифровки и восстановить содержимое хранилища.

Главное преимущество такого подхода заключается в том, что не требуется вручную переносить всю логику прошивки на Python. Достаточно восстановить необходимые зависимости и предоставить функции ожидаемые данные и состояние памяти.

## Итог

В результате был создан программный эмулятор необходимой части окружения прошивки RP2040 на базе Unicorn Engine. Он позволяет загружать исходный дамп, выполнять оригинальный ARM-код и моделировать необходимые обращения к аппаратным компонентам.

С его помощью удалось выполнить оригинальную функцию проверки PIN и перебрать пространство из `0000`–`9999` без физического ввода на устройстве. После этого через оригинальную функцию расшифровки было восстановлено зашифрованное хранилище и сформирован образ FAT12.

Таким образом, эмуляция стала отдельным вектором решения задачи: вместо изменения прошивки или непосредственного взаимодействия с устройством мы перенесли выполнение интересующей нас логики в программную среду и получили возможность управлять её входными данными напрямую.
